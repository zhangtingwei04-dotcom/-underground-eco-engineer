# 寄養、寵物照片郵件與緊急通知系統規劃

> 文件狀態：已確認的設計規格（尚未代表程式已實作）
> 整理日期：2026-11-06
> 適用專案：《鱗片與種子：地下生態物語》

本文件保存玩家已確認的寄養、每週寵物照片郵件、電子郵件驗證及緊急通知決策。後續開發以本文件為依據；若有新決策，應更新本文件並保留 Git commit 歷史，不以聊天記憶作為唯一規格來源。

## 1. 設計原則

- 寵物安全與照護品質優先於遊戲便利性。
- 寄養不會改變寵物所有權；寵物仍屬於玩家。
- NPC 是否能寄養，依個性、照護能力、生活條件、專業及玩家關係綜合判斷，不能只看好感度。
- 金錢不是寄養的唯一門檻。
- 玩家不必為了避免錯過重要事件而被迫每日登入。
- 郵件與推播是遊戲外通知管道；所有事件仍須在遊戲內保存完整紀錄。
- 本文件是設計規格，不表示郵件、推播、照片生成或伺服器功能已經完成。

## 2. 寄養服務

### 2.1 寄養提供者

遊戲提供兩類寄養來源：

1. **NPC 個人寄養**
   - NPC 依個性、意願、照護技能、專業知識、生活作息、可用空間及設備決定是否接收寵物。
   - 並非所有 NPC 都能寄養。
   - 高好感度不能凌駕於安全條件；若 NPC 缺乏合適空間、時間或設備，即使關係良好也不能接收。
2. **專門寄養中心**
   - 提供標準化的寄養服務、狀態查詢及照護報告。
   - 可提供較完整的專業照護；特殊付費服務可以存在，但不應讓金錢成為取得基本安全照護的唯一途徑。

### 2.2 寄養資格與交換方式

- 友好型 NPC：達到指定友好／信任門檻後可免費寄養。
- 互助型 NPC：可能要求玩家完成任務、提供材料或交換研究成果。
- 特殊 NPC：可能要求符合其專業或個人條件的非金錢交換。
- 寄養中心：以免費或任務／材料交換為主；可另設特殊付費服務。
- 是否可寄養仍須通過 NPC 能力及生活條件檢查。

### 2.3 照護方式

照護品質與內容依寄養提供者而異：

- 一般 NPC 依其技能、經驗與能力進行日常照護。
- 專業 NPC、醫療相關 NPC 或寄養中心可提供更完整的專業觀察與照護。
- 不同提供者的照護頻率、回報習慣、互動方式及可提供服務可以不同。
- 寄養期間需留下餵食、飲水、清潔、環境調整、觀察、健康異常及處置紀錄。

### 2.4 寄養期限

免費／彈性寄養與固定期限並存：

- 部分 NPC 可接受無固定期限或彈性寄養，玩家可協調接回。
- 部分 NPC 有固定期限或個人條件。
- 寄養中心提供 3、7、14、30 天等固定方案。
- 玩家可以查看預計接回日期與寄養規則。
- 期限將至時應預先提醒；不得在未清楚告知的情況下任意轉移寵物或改變所有權。

### 2.5 寄養期間的玩家互動

- NPC 依個人日程與性格決定探訪、互動及回報頻率。
- 寄養中心提供標準化探訪及狀態報告。
- 玩家可以查看寵物狀態、照護紀錄與可探訪時間，並依寄養規則提出接回。
- 即使玩家不能即時登入，重要狀態及事件也要保留，之後可查閱。

### 2.6 所有權與操作限制

寄養不等於轉讓。寄養中的寵物仍由玩家擁有。寄養提供者不得擅自出售、繁殖、釋放、轉讓或改變寵物所有權。任何涉及寵物去向的重大決定，均須遵守玩家授權及遊戲的動物安全規則。

## 3. 寄養期間的健康事件與緊急處置

採用依事件嚴重程度分級的處理方式：

- **一般狀況**：寄養提供者依能力自行處理，留下紀錄，並在例行報告中告知玩家。
- **需要注意的狀況**：提供者先採取適當照護並通知玩家，讓玩家了解狀況及後續觀察。
- **重大或危急狀況**：立即啟動緊急通知，提供者先執行必要且合乎能力範圍的緊急照護；不得為等待玩家登入或回覆而延誤必要處置。
- 若需要超出提供者能力的醫療處置，應依遊戲設定聯絡合適的醫療／專業 NPC 或服務，並向玩家說明。
- 事件原因未確認時，必須標示為「待確認」或「可能原因」，不得把推測寫成確定診斷。
- 每次處置均保存時間、狀態、負責者、採取措施及結果。

### 3.1 緊急事件報告內容

重大事件通知應盡可能包含完整事件報告：

1. 寵物當下照片（若能安全取得且有助於判斷）。
2. 健康狀態與可用指標，例如體重、活動力、食慾及異常指標。
3. 寄養環境資料，例如溫度、濕度、光照、通風及設備狀態。
4. 發生時間、觀察到的症狀、事件經過及可能原因。
5. NPC／寄養中心已採取的措施及處置時間。
6. 是否已聯絡醫療或專業人員。
7. 待玩家決定的事項、建議選項及處理時限。
8. 最新狀態與後續追蹤紀錄。

資料不存在或尚未測量時應標示「未取得」，不可虛構數值。

## 4. 玩家通知與電子郵件帳戶

### 4.1 收件信箱

- 預設使用玩家註冊遊戲時提供的電子郵件。
- 玩家可以改用其他收件信箱。
- 更換信箱後，新信箱必須完成驗證才可接收通知。
- 啟用遊戲外通知前，必須讓玩家清楚同意通知用途。
- 信箱地址屬個人資料，不得在公開玩家頁面顯示。
- 郵件通知、每週照片郵件及手機推播分開管理；關閉週報不能意外關閉緊急通知。

### 4.2 通知管道

- 一般通知與每週照片：電子郵件。
- 需要注意的事件：電子郵件。
- 非常嚴重／極度危急事件：電子郵件加手機推播。
- 手機推播必須由玩家明確授權；瀏覽器或裝置不支援時，仍使用已驗證電子郵件作為可用管道。
- 推播權限或郵件傳送失敗時，遊戲內仍須保留事件，並顯示通知狀態；不得假稱玩家已收到通知。

### 4.3 緊急提醒與確認

- 提醒次數與間隔依事件嚴重程度決定，設合理上限，避免短時間重複轟炸。
- 玩家確認收到同一事件後，停止該事件一般性的重複提醒。
- 若事件惡化、出現新症狀或需要新的重大決定，可以再次通知。
- 通知確認只代表玩家已收到資訊，不應被視為同意任何高風險或不可逆處置。
- 玩家可以透過手機推播的安全快速回覆、電子郵件中的安全連結或登入遊戲處理需要玩家決定的事項。
- 遠端操作應使用短效、不可猜測、限用途的安全憑證；重要或不可逆決策應要求重新驗證身分，並保存操作紀錄。
- 推播與郵件內容應避免洩露不必要的個人資料。

## 4.4 玩家遠端決策與安全授權（已確認）

採用依事件嚴重程度提供不同遠端操作的方式：

- 一般事件可能只需要查看與確認通知。
- 需要處理的事件可提供 NPC 建議的處置方案供玩家選擇。
- 較嚴重事件可提供聯絡醫療／專業 NPC、安排接回寵物等選項（以事件實際可行性及寄養規則為準）。
- 重大或不可逆決策必須額外驗證身分，並清楚展示後果、成本及可否撤回。
- 遠端選項不得取代必要的即時安全照護；寄養提供者仍須先採取能力範圍內的必要措施。
- 所有玩家遠端操作均保存操作者、時間、選項、驗證結果及執行結果。

## 5. 每週寵物照片郵件

### 5.1 預設與數量

- 預設每週寄送 **3 張**。
- 玩家可自行設定每週 **1～5 張**。
- 玩家可以暫停或取消每週照片郵件。
- 若當週沒有足夠且合適的照片，不得用不符合實際狀態的照片硬湊數量；可以少寄並在郵件中簡短說明。

### 5.2 照片類型

玩家可選擇希望收到的照片類型，或交由系統挑選：

- 全身照：呈現完整外觀、體型與成長。
- 近距離特寫：呈現花紋、鱗片、眼睛等個體細節。
- 進食照：記錄進食情境。
- 睡覺照：記錄休息姿態。
- 活動照：記錄探索、攀爬、游動等自然行為。
- 生活紀錄照：呈現寵物在飼養箱或寄養環境中的日常。

### 5.3 照片生成與真實性

採用「遊戲依實際狀態生成」並融合「NPC 個人拍攝風格」的方式：

- 寵物的物種、花紋、體型、年齡、個體特徵與當週狀態必須以遊戲資料為準。
- 可以安排安全且合理的構圖，例如在熟悉的躲避屋旁、攀爬木頭上或水盆旁。
- 不可偽造寵物曾經歷的事件、健康狀態或未曾到過的環境。
- 寄養期間可呈現寄養 NPC 的拍攝風格與實際寄養環境。
- NPC 拍攝風格可以不同：擅長構圖、偏好自然瞬間，或偶爾拍到有趣角度、失焦及意外畫面。
- 若遊戲狀態不足以支持某種照片情境，應改選其他真實可呈現的照片類型。

### 5.4 郵件內容

每封每週照片郵件包含：

- 寵物名稱及個體識別資訊。
- 照片與拍攝日期。
- 簡短生活紀錄，例如活動、進食、休息或成長變化。
- 若處於寄養期間，註明寄養 NPC／中心及當週照護摘要。
- 不以照片取代正式健康報告；健康異常另走事件通知流程。

## 6. 通知設定介面

玩家設定中應分開控制：

- 每週照片郵件：開／關。
- 每週照片數量：1～5 張，預設 3 張。
- 照片類型：自選或交由系統挑選。
- 一般電子郵件通知：開／關。
- 緊急電子郵件：獨立設定。
- 緊急手機推播：授權後開／關。
- 收件電子郵件：顯示驗證狀態及更換流程。
- 可查看最近寄送紀錄、通知失敗狀態及事件歷史。

通知偏好應保存於玩家帳戶資料，並與本機遊戲設定區分；若尚未登入或尚未完成帳戶驗證，不應假設可寄送外部郵件。

## 7. 技術實作方向與依賴

本系統不能只靠 Phaser 前端完成。正式上線前需規劃可信任的伺服器端服務：

- 帳戶與電子郵件驗證：安全的註冊信箱驗證、更換信箱驗證及通知同意紀錄。
- 排程服務：每週照片郵件排程、寄養報告及事件提醒。
- 郵件服務：寄送、退信處理、重試、寄送紀錄及防止重複寄送。
- 推播服務：裝置／瀏覽器授權、訂閱管理、失效訂閱清理及推播回執。
- 事件服務：嚴重程度判斷、事件狀態、提醒節流、玩家確認與重新通知規則。
- 照片服務：依寵物穩定個體資料及當週狀態產生／選取照片，保留生成依據與時間。
- 安全服務：登入驗證、權限檢查、短效操作憑證、敏感操作再次驗證及稽核紀錄。
- 存檔資料：寄養合約／期限、提供者、照護紀錄、事件紀錄、郵件偏好、照片寄送設定及通知狀態均需版本化保存。

**重要限制：** GitHub Pages 是靜態網站託管，不能單獨安全地保存郵件服務密鑰、執行可靠的排程寄送或處理私密推播憑證。正式實作時必須搭配後端／雲端函式及資料庫；任何 API 金鑰或服務密鑰不得寫入前端程式碼或公開 GitHub 儲存庫。

## 8. 建議開發順序

1. 先完成遊戲內寄養資料模型、NPC 資格判定、寄養期限與照護紀錄。
2. 完成寄養狀態、健康事件分級與遊戲內事件紀錄。
3. 完成玩家通知偏好與帳戶電子郵件驗證流程。
4. 接入伺服器端郵件服務，先實作一般報告與每週照片郵件。
5. 完成照片選擇／生成規則及每週排程。
6. 接入手機推播服務與授權管理。
7. 完成緊急事件完整報告、提醒節流、玩家遠端確認／決策及安全驗證。
8. 測試離線、通知失敗、信箱更換、推播拒絕、重複事件、事件惡化及資料遷移。

每一階段先完成可測試的最小功能，不把尚未接入的外部服務描述成已可使用。
