# 《鱗片與種子：地下生態物語》長期跨平台策略

**決策狀態：** 使用者於 2026-11-07 確認採用 D 方向：長期跨平台遊戲，支援跨裝置延續同一個遊戲世界與存檔。本文件記錄長期目標與分階段技術原則，不代表各平台功能已實作，也不代表現在開始多平台同步開發。

## 一、產品願景

《鱗片與種子》長期應讓玩家能在不同裝置進入同一個歐姆世界，延續相同角色、寵物個體、研究紀錄、NPC 關係、家庭歷史、居住環境與世界事件。

核心體驗不是各平台各自一份進度，而是：
- 一個玩家帳號可連結多個受支援裝置。
- 同一個世界／存檔欄位可在電腦、手機及網頁之間延續。
- 玩家在裝置 A 儲存並同步後，可在裝置 B 讀取最新進度。
- 網路暫時中斷時，允許在明確標示的離線模式下繼續遊玩，連線恢復後再安全同步。
- 不同平台可以有各自適合的 UI、操作及效能調整，但不可因此分裂成互不相通的遊戲世界。

跨平台不等於必須立即支援多人連線；第一個目標是單一玩家在多裝置間安全接續同一個世界。多人共同世界屬於獨立且尚未確認的後續議題。

## 二、平台發展順序

### 階段 0：跨平台基礎準備（現階段逐步建立）
- 保留目前 Phaser + JavaScript 網頁開發主線，不因平台願景而更換引擎。
- 新增功能時，避免把核心遊戲規則直接綁定瀏覽器 DOM、localStorage 或單一裝置 API。
- 將遊戲核心資料、畫面呈現、平台能力及存檔服務逐步分離。
- 存檔格式加入明確 schemaVersion、資料識別碼、建立／更新時間及必要的遷移規則。
- 區分玩家帳號資料、世界存檔、角色／生物個體資料、裝置偏好設定；語言、音量及控制方式等裝置偏好不應不必要地覆蓋其他裝置設定。
- 先確保現有網頁版穩定、可玩及可備份，不為抽象的跨平台需求建立過度複雜架構。

### 階段 1：完整網頁版
- 先完成核心玩法、玩家流程、地下研究設施、生物照護、NPC、世界探索與基本存檔。
- 支援桌面瀏覽器及手機瀏覽器的合理操作與版面。
- 建立可測試的存檔匯出／備份及還原流程。
- 明確區分訪客本機存檔與正式帳號存檔；在玩家登入、註冊或遷移時避免覆蓋既有進度。

### 階段 2：存檔與帳號跨裝置基礎
- 在擴展原生平台前，先正式化帳號身分、世界／存檔欄位識別、存檔版本遷移、本機備份、雲端同步與衝突保護。
- 確認同一帳號能在不同瀏覽器／裝置安全讀取同一份世界進度；離線分歧不得靜默覆蓋。
- 這個階段先讓跨裝置資料流程可靠，不要求立即推出所有原生 App。

### 階段 3：電腦桌面版
- 在網頁版核心與存檔同步基礎穩定後，評估以桌面容器包裝現有 Phaser 遊戲。
- Electron 與 Tauri 均列為候選，不提前定案：Electron 與現有 Web 技術整合直接；Tauri 可評估較精簡的應用程式封裝，但需衡量原生整合與維護成本。
- 桌面版需處理安裝、更新、視窗、檔案備份、離線啟動、解析度及控制器等平台細節。
- 不以桌面包裝為理由重寫核心遊戲。

### 階段 4：手機 App 版
- 評估以 Capacitor 等 Web Native 容器包裝既有網頁遊戲，再依實際需求補上 iOS／Android 原生能力。
- 針對觸控、直式／橫式構圖、文字尺寸、耗電、記憶體、背景暫停與網路中斷重新驗證。
- 手機版不是單純縮小桌面 UI；保留獨立手機介面設計。
- 依 Apple App Store 與 Google Play 當時的審核、帳號、付款及隱私規範調整。

### 階段 5：主機及其他平台評估
- 只有在核心遊戲成熟、玩家需求明確且技術與商業成本合理時，才評估主機或其他新平台。
- 重新檢查平台輸入、控制器、效能、儲存、帳號、商店審核及更新政策。
- 不將主機版列為目前開發承諾或硬性里程碑。

## 三、建議的長期技術分層

1. **遊戲核心層：** 世界規則、玩家、寵物個體、NPC、家庭、研究、經濟及事件結算；盡可能不直接依賴特定平台。
2. **呈現與輸入層：** Phaser 場景、UI、滑鼠、觸控、鍵盤及控制器；不同裝置可使用不同版面與操作。
3. **平台能力介面層：** 統一封裝本機儲存、檔案、通知、音訊、網路狀態及平台生命週期；各平台提供自己的 adapter。
4. **存檔與同步層：** 序列化、版本遷移、本機快取、雲端上傳下載、修訂版號、衝突處理及備份。
5. **帳號與後端層：** 身分驗證、玩家資料權限、世界存檔資料庫及伺服器端驗證。

這是逐步重構的目標架構，不要求現在一次建立所有抽象介面或微服務。優先抽離已經出現跨平台需求的能力。

## 四、存檔與世界連續性規則

- 每個世界及存檔欄位應有穩定且唯一的 ID；玩家帳號 ID、世界 ID、裝置 ID 與存檔修訂版號不可混為一談。
- 存檔資料需有 schemaVersion，未來更新時可逐版遷移；不得因讀取新舊版本差異而直接重置玩家資料。
- 重要個體與歷史需保留穩定 ID，例如寵物個體、NPC、家庭成員、研究紀錄及重要事件，不能只依陣列位置識別。
- 世界時間及離線進展需採可驗證的時間基準與低頻結算；不可完全信任玩家裝置本機時鐘，亦不可要求所有 NPC 持續即時運算。
- NPC 離線生活、環境變化及資源恢復沿用既有低頻結算原則，並確保同一段時間不會因不同裝置重複結算。
- 玩家設定可區分帳號層與裝置層；裝置操作偏好不應無意間覆蓋另一裝置的設定。
- 提供玩家可理解的同步狀態、最後同步時間、備份與還原方式。

## 五、目前既有存檔基礎與後續檢視事項

截至 2026-11-07 檢視 GitHub main：
- `src/systems/save-system.js` 已有統一存檔入口，支援訪客／雲端模式及訪客資料遷移。
- `src/systems/cloud-save-system.js` 已使用 localStorage 作本機存檔，並以 Supabase `player_saves` 資料表同步帳號存檔；雲端帳號讀取時會比較本機與雲端的更新時間。
- `src/systems/terrarium-save-system.js` 另有一套獨立 localStorage 生態箱存檔。
- 因此專案已有本機與雲端存檔的初步基礎，但尚不能據此宣稱已完成安全的跨裝置同步。現有更新時間比較及單筆 upsert 尚未形成完整的修訂版衝突控制、離線佇列、跨裝置衝突保留與正式帳號復原流程；兩套存檔的整合關係也需進一步檢查。
- 後續應先盤點現有存檔呼叫點、Supabase schema／Row Level Security、登入流程及生態箱資料來源，再規劃漸進式整合；不得在未確認資料遷移與備份前直接替換存檔系統。
- 本文件記錄的是平台策略與技術檢視，不代表已修改上述程式或完成後端安全審核。

## 六、開發優先順序與不做事項

優先順序：
1. 遊戲穩定與核心玩法。
2. 存檔資料結構、版本遷移及資料完整性。
3. 本機備份、雲端同步與衝突保護。
4. 桌面與手機操作體驗。
5. 桌面／手機原生封裝。
6. 主機及其他平台評估。

目前不做：
- 不因跨平台目標立即更換 Phaser。
- 不同時維護多套獨立遊戲核心。
- 不急著建立即時多人世界或複雜微服務。
- 不允許舊存檔在同步時靜默覆蓋較新的世界進度。
- 不把支援所有平台當成發行前必須完成的條件。

**最終原則：一個歐姆世界、一份可延續的玩家進度、多種適合各裝置的遊玩入口。穩定性、資料安全與可持續維護優先於平台數量。**
