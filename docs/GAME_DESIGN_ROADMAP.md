# 《鱗片與種子：地下生態物語》主遊戲企劃與開發路線圖

> 版本：V1.0 開發總綱  
> 遊戲方向：綜合型生活模擬 × 生態經營 × 探索冒險  
> 遊戲節奏：平衡型  
> 技術基礎：Phaser 3.80.1、JavaScript ES Modules、GitHub Pages

## 一、遊戲願景

玩家從一間小型地下生態研究站開始，逐步建立屬於自己的地下生態世界。核心樂趣來自照顧生物、設計棲地、研究物種、經營資源、認識研究站居民，以及探索逐步開放的地下區域。

遊戲以「照顧生命與理解生態」為核心，不以懲罰玩家未每日登入為主要挑戰。離線時間模擬採溫和、可理解、可補救的平衡設計。

## 二、核心遊戲循環

1. 回到研究站：查看研究委託、資金、物資與生物狀態。
2. 巡視生態缸：觀察溫度、濕度、光照、清潔度與生物需求。
3. 照顧生物：餵食、補水、清潔、休息、觀察與健康照護。
4. 建造棲地：配置底材、躲藏處、植物、石木造景及設備。
5. 研究與收集：完成觀察紀錄、解鎖物種資料、取得研究點數。
6. 探索地下區域：採集素材、發現新物種、觸發事件與任務。
7. 經營與社交：出售合法繁殖／採集成果、購買物資、與 NPC 建立關係。
8. 儲存進度：自動存檔與手動存檔，跨次遊玩保留成果。

## 三、主要系統

### A. 玩家與研究站
- 玩家資料、資金、研究點數、聲望、背包與任務。
- 研究站房間逐步解鎖：飼育室、植物室、研究室、倉庫、休息區與探索入口。
- 以木質、石材、苔蘚及暖光為主要介面材質。

### B. 生物飼養
- 每隻生物有獨立個體資料：物種、正式名稱／暱稱、年齡、成長階段、健康、飢餓、水分、壓力、性格、基因與觀察紀錄。
- 需求依物種資料設定，不把同一套溫濕度規則套用所有生物。
- 飼養行為包含餵食、補水、清潔、環境調整、觀察及休息。
- 平衡型預設不讓生物因短時間離線而死亡；嚴重疏忽先以警告、狀態異常及可補救事件呈現。
- 真實飼養知識與遊戲數值分離，避免把遊戲簡化機制誤當成真實飼養建議。

### C. 生態缸與建造
- 多個生態缸獨立保存。
- 以格位／座標配置底材、洞穴、石頭、木頭、植物、水盆、燈具與設備。
- 物件有價格、分類、尺寸、環境效果及適用棲地。
- 建造前檢查空間、物資與棲地適配；可移動、旋轉、收納及拆除。
- 任何拆除或搬遷操作都先確認活體安全，不直接移除仍有生物的棲地。

### D. 生態與環境模擬
- 環境指標：溫度、濕度、光照、通風、潔淨度與水源。
- 植物、設備、地形與房間條件共同影響環境。
- 以物種棲地需求判定舒適度，顯示可理解的改善建議。
- 模擬採遊戲化區間與合理速度，提供清楚提示，不製造不必要的即時壓力。

### E. 探索、研究與圖鑑
- 地下區域分層解鎖，各區有不同生態主題、素材、事件及發現。
- 研究行為取得研究點數與圖鑑資料。
- 圖鑑記錄物種特徵、棲地、習性、已觀察行為與玩家發現。
- 探索有簡單可玩的移動、互動、採集及事件選擇，不只顯示文字。

### F. NPC、任務與關係
- NPC 有完整姓名、文化背景、職業、個性、喜好、日程及關係資料。
- 任務包含研究委託、採集、照護、建造與故事事件。
- 關係依互動、選擇與時間變化；階段與稱呼依關係進度調整。
- 對話與事件資料和場景 UI 分離，支援多語系。

### G. 經濟與進度
- 資金用於購買物資、設備、擴建與研究。
- 研究點數解鎖新物種資料、工具、區域與建造配方。
- 任務獎勵與商店價格需維持經濟平衡。
- 不以付費或強迫每日登入作為核心進度門檻。

## 四、開發階段與可玩交付標準

### Phase 0：專案健康與啟動鏈修復
- 確認入口、場景、系統匯入路徑與 GitHub Pages 啟動流程。
- 確認「開始遊戲」確實能載入／建立存檔並進入遊戲。
- 確認本機存檔可用；雲端不可用時不覆蓋或清除舊資料。
- 檢查現有系統重複、未接線及介面呼叫不一致處。
- 交付：玩家可從入口進入遊戲，重新整理後仍保留進度。

### Phase 1：第一個可玩版本（Vertical Slice）
- 地下研究站主畫面、玩家狀態列、主要導覽。
- 至少一隻初始生物可查看狀態。
- 可執行餵食、補水、清潔及觀察，行動後數值正確變化。
- 生態缸顯示環境狀態，並能切換／管理。
- 自動存檔、重新進入後正確還原。
- 交付：不依賴開發者工具，玩家可完成一輪完整照護循環。

### Phase 2：生態缸建造與環境
- 物品庫、背包、建造模式、放置／移動／移除。
- 物件效果影響環境，環境適配影響生物狀態。
- 交付：玩家可自行設計並保存一座可用棲地。

### Phase 3：研究、圖鑑與探索
- 探索地圖、採集、事件、研究點數及圖鑑解鎖。
- 交付：玩家有可重複遊玩的探索與收集目標。

### Phase 4：NPC、任務與生活內容
- NPC 資料、日程、對話、任務、關係及事件。
- 交付：研究站居民與任務形成長期遊戲目標。

### Phase 5：經濟、擴建與內容擴充
- 商店、資源循環、房間擴建、更多物種與棲地主題。
- 交付：完整的中長期經營成長循環。

### Phase 6：美術、音效、平衡與發布品質
- 正式像素素材逐項替換暫代素材。
- 直式與橫式分別適配，不拉伸同一張背景。
- 多語系檢查、效能、存檔相容性、觸控操作及錯誤處理。
- 交付：穩定、可持續更新的正式遊戲版本。

## 五、寄養、寵物照片郵件與緊急通知

- 寄養、NPC 資格、照護差異、期限、所有權保護、緊急事件分級、電子郵件驗證、每週照片郵件及手機推播的已確認規格，集中記錄於 [SYSTEM_DESIGN_PET_BOARDING_AND_MAIL.md](./SYSTEM_DESIGN_PET_BOARDING_AND_MAIL.md)。
- 每週照片預設 3 張，玩家可設定每週 1～5 張，並選擇照片類型。
- 一般與每週照片通知使用電子郵件；非常嚴重／極度危急事件使用電子郵件加手機推播。
- 緊急報告需提供可取得的寵物照片、健康與環境資料、事件經過、NPC 已採取措施及後續建議；資料未取得時不得虛構。
- 遠端決策可透過推播快速回覆、郵件安全連結或登入遊戲；重要／不可逆操作需重新驗證身分。
- 本系統需要伺服器端排程、郵件／推播服務與安全資料儲存，不能只靠 GitHub Pages 前端完成。
- 文件中的已確認規格與待決事項分開管理；未實作的功能不得宣稱已上線。

## 六、工程架構原則

- Scene 只負責畫面呈現與玩家輸入；規則放在獨立 System。
- 資料定義、物種設定、NPC 設定、任務及多語系字典與程式邏輯分離。
- 存檔採版本化資料結構，新增欄位需有遷移與預設值。
- 每個功能要有明確資料來源、狀態更新與存檔路徑。
- 先做可玩的暫代 UI，再逐步替換正式美術。
- 不在未確認前重置玩家存檔、資料庫或雲端資料。
- 優先保留既有功能；大型架構調整先提出風險與遷移方式。
- 每次提交後檢查匯入路徑、語法、資料格式與場景流程；無法實際啟動測試時明確標示，不宣稱已通過遊戲實測。

## 六、介面與美術規範

- 精緻、溫暖、奇幻的地下生態研究站像素風。
- 木質外框、木紋面板、木雕按鈕、暖金屬裝飾；搭配石材、苔蘚、菌菇、發光植物與柔和粒子。
- 避免冷色全息面板成為主要視覺。
- 遊戲標題與 UI 文字必須由語言系統動態呈現，不烘焙在背景圖片。
- 預設英文，支援繁體中文、簡體中文、日文、韓文、泰文、法文、德文、西班牙文及巴西葡萄牙文。
- 保留既有 80%～120% 畫面縮放範圍。

## 七、每階段驗收方式

每個階段至少檢查：
1. 場景能否正常進入與返回。
2. 主要按鈕在手機直式與橫式均可觸控。
3. 操作是否真的改變遊戲資料，而非只有文字或裝飾。
4. 存檔、重新整理、重新進入是否能還原。
5. 語言切換是否影響新增介面。
6. 舊功能與舊存檔是否仍可使用。
7. 發現問題時先修復，不以新增更多功能掩蓋問題。

## 九、地下探索、NPC 私人領地、生物登記與雙名字制度

- 地下探索、每週個人化地點、永久探索地圖、特殊事件紅色驚嘆號、NPC 私人領地、季節性生態、物種花紋分布、保育許可、生物登記所與玩家雙名字制度的完整已確認規格，集中記錄於 [SYSTEM_DESIGN_EXPLORATION_REGISTRY_AND_IDENTITY.md](./SYSTEM_DESIGN_EXPLORATION_REGISTRY_AND_IDENTITY.md)。
- 玩家親自探索為核心；每週探索地點依玩家進度與個人世界資料生成，探索完成後永久收錄，並可隨季節與生態事件持續變化。
- 部分 NPC 擁有私人領地；進入權限依個性、好感、信任、心情、季節、特殊時間與聲望等條件管理。初次通常由 NPC 帶領，信任建立後才可能授予獨自探索權限；關係惡化時可收回。
- 特殊事件以地圖紅色驚嘆號提示；一般事件保留，少數限時事件不得永久阻斷主要劇情或必要物種解鎖。
- 物種花紋與棲地、季節及特殊區域連動；普通地點保留極低機率發現特殊花紋的可能。
- 特殊物種能否帶離原棲地及飼養，依保育規則與綜合審核決定；高階聲望是重要條件之一，但不保證核准。
- 玩家初次抵達地下王國時，須前往生物登記所辦理身分登記。登記所同時管理居民／外來者身分、生物登記及特殊物種許可。
- 地上來訪者採雙名字制度：地下王國日常使用地下名字；地上現實名字保密，原則上只在地上研究所來信或其他明確特殊情況顯示。
- 本節所連結文件為設計規格，不代表上述系統已完成程式實作；具體數值、行政細節與生成演算法仍列為待決事項。

- V26.0 NPC 情感、心情、長期記憶、個人生活、關係階段、稱呼、告白與專屬歌曲等獨立規格，記錄於 [SYSTEM_DESIGN_NPC_EMOTION_MOOD_MEMORY.md](./SYSTEM_DESIGN_NPC_EMOTION_MOOD_MEMORY.md)。

- 慢生活原則：NPC 有自己的生活與情緒，但重要事件需保留可回顧，不以短暫未登入作為普遍懲罰。

## 十一、語言自動判別、偏好保存與雲端同步

- 遊戲支援語言維持既定的 10 種：英文、繁體中文、簡體中文、日文、韓文、泰文、法文、德文、西班牙文及巴西葡萄牙文。
- 首次進入且尚無既有語言偏好時，依裝置／瀏覽器語言自動判別；不使用 GPS、所在地或 IP 地區決定遊戲語言。
- 裝置有多個偏好語言時，依照偏好順位逐一比對，使用第一個可支援的語言；全部不支援時預設英文。
- 語言相同但地區版本不同時，採用最接近的支援版本。例如葡萄牙葡萄牙語使用遊戲支援的巴西葡萄牙文。
- 玩家手動切換語言後，手動選擇優先於裝置語言；後續啟動、裝置語言變更或更換裝置均不得自動覆蓋既有帳號語言偏好。
- 訪客玩家手動選擇語言時，先保存於目前裝置；日後註冊或登入時再同步雲端。若帳號原本已有語言偏好，以帳號設定為準，避免訪客裝置設定意外覆蓋帳號偏好。
- 已登入且雲端有語言偏好時，清除本機資料或重新安裝後，優先恢復雲端設定；未登入或雲端無紀錄時，才依裝置語言重新判別。
- 語言偏好屬於帳號設定，應與玩家所在地、時區及遊戲內世界地區分離。
- 實作時需處理瀏覽器語言 API 不可用、語言代碼正規化、首次登入同步衝突、離線訪客設定及雲端同步失敗等情況；同步失敗不得阻止玩家遊玩。
- 本節為已確認的設計規則；雲端帳號與同步服務尚需後端支援，未完成前不得宣稱跨裝置同步已上線。

## 十二、寵物個體羈絆、生命成長與真實生物知識

- 寵物個體羈絆、物種差異化性格、後天適應、生命階段、歐姆地下生命共鳴、真實生物資料標示、物種百科與研究成果實際用途的完整規格，集中記錄於 [SYSTEM_DESIGN_PET_BOND_AND_BIOLOGY_KNOWLEDGE.md](./SYSTEM_DESIGN_PET_BOND_AND_BIOLOGY_KNOWLEDGE.md)。
- 玩家與寵物的熟悉及適應關係必須依物種真實生物習性與認知能力設計；內部可使用多項指標，外部以真實行為與觀察紀錄呈現，不顯示單一「愛主人」數值。
- 每隻寵物有符合物種範圍的個體差異，並可受長期生活經驗影響；不得將所有動物擬人化。
- 生命階段、成長速度與自然壽命依物種設定。遊戲以真實時間記錄，幼體初期可較快成長，之後逐步放慢並接近現實成長速度。
- 歐姆地下土地存在虛構的「生命共鳴現象」：所有進入地下的生物可能受到不同程度影響，幼年期加速作用較明顯、之後逐漸減弱；不得跳過正常發育或直接縮短自然壽命。
- 遊戲知識以現實生物科學為主，少數奇幻內容清楚標示為歐姆世界觀設定；資料分為真實科學資料、科學推測及世界觀設定，並提供可查閱的研究／機構來源與查證日期。
- 初次發現解鎖物種基礎百科，深入資料透過觀察與研究逐步解鎖；不要求玩家一定擁有該物種才能學習。

## 十四、跨平台支援、效能與穩定性要求

**狀態：核心方向已確認；相容性矩陣、效能預算與測試裝置待逐步建立。**

### 14.1 支援平台與操作方式
- 遊戲需同時支援手機與電腦遊玩。
- 手機目標環境為 iOS、Android 的主流瀏覽器；以觸控為主要輸入方式。
- 電腦目標環境為主流桌面瀏覽器；支援滑鼠與鍵盤操作。
- 核心功能不得因裝置或輸入方式不同而缺失；若操作有平台差異，需提供等效替代方式。

### 14.2 自適應畫面
- 依螢幕尺寸、解析度、長寬比、方向與輸入方式調整版面。
- 手機直式與橫式需分別適配；桌面版需善用較寬畫面。
- 不得只把桌面 UI 等比例縮小到手機，也不得以拉伸背景或硬裁切作為唯一適配方式。
- 重要按鈕、文字、資訊及互動區域在小螢幕仍須清楚且可操作。
- 保留既有 80%～120% 畫面縮放設定，並確保縮放後不造成介面重疊或操作區域跑版。

### 14.3 效能與防卡死
- 控制場景物件、事件監聽器、計時器、動畫、貼圖、音效及快取資源的生命週期，避免重複建立後未清理。
- 避免主執行緒執行過重或無限迴圈工作；大量資料處理應分批或採非阻塞方式。
- 圖片、音效及場景資源採合理載入策略；載入失敗需有錯誤提示與可恢復流程，不得無限等待。
- 網路、存檔及雲端同步需處理逾時、失敗、重試與資料衝突；非必要服務不可阻斷本機核心遊玩。
- 長時間遊玩、重複進出場景及連續操作後，仍需維持合理效能，不可出現持續性資源累積。
- 發生非預期錯誤時，盡可能安全保存可保存的進度、提示玩家並提供返回或重新嘗試方式，避免黑畫面或整個遊戲無回應。

### 14.4 跨平台驗收
1. 手機直式、手機橫式與桌面不同視窗尺寸的版面。
2. 觸控、滑鼠與鍵盤主要操作流程。
3. 場景進出、重新整理、存檔、載入與恢復流程。
4. 長時間遊玩及反覆切換場景後的效能與資源釋放。
5. 慢速網路、離線、資源載入失敗、雲端服務失敗等情況。
6. JavaScript 錯誤、未處理 Promise rejection、非同步流程逾時與錯誤恢復。
7. 以實際裝置和瀏覽器建立測試紀錄；未實際測試的平台不得標示為已驗證。

本節是正式產品與工程要求，不代表現有版本已完成所有平台相容性測試，也不代表已保證絕無錯誤。需隨開發階段持續實測、修正與回歸驗收。


## 十五、最高開發原則：穩定遊玩優先於功能完整

**狀態：已確認；適用於所有開發階段與所有系統。**

### 15.1 最高優先級
遊戲首先必須能在手機與電腦正常啟動、操作並持續遊玩。功能數量、模擬深度與系統複雜度都不能凌駕於可玩性、效能、穩定性及存檔安全之上。

### 15.2 複雜系統的降級與移除策略
若某項複雜系統影響遊戲穩定或跨平台效能，依序採取：
1. 降低更新頻率，避免不必要的即時運算。
2. 改為事件觸發或低頻批次結算。
3. 延後到玩家進入相關場景或真正需要時才計算。
4. 減少資料量、物件數、畫面特效及背景工作。
5. 以重要摘要與關鍵狀態取代完整細節模擬。
6. 若仍無法達到穩定可玩要求，暫緩、關閉或移除該功能。

不得因功能已投入開發、設計內容豐富或追求系統完整，而保留會使遊戲卡死、當機、嚴重卡頓或無法操作的實作。

### 15.3 保護核心遊戲體驗與資料
- 優先保留核心遊戲循環及玩家可感知的重要體驗，刪除不必要的內部複雜度。
- 簡化或移除功能時，須評估既有存檔、資料格式與玩家進度；必要時提供版本遷移、預設值或安全回復機制。
- 不得以雲端同步、非必要網路服務或背景模擬失敗阻斷本機核心遊玩。
- 不得為了效能任意破壞核心玩法；應先簡化實作，再判斷是否需要縮減功能範圍。

### 15.4 開發與驗收優先順序
1. 可啟動、可操作、可持續遊玩。
2. 存檔安全、錯誤恢復與跨裝置基本相容。
3. 手機與電腦的效能、畫面及輸入適配。
4. 核心玩法完整且穩定。
5. 進階系統的深度、細節與內容擴充。

本原則適用於 NPC 自主生活與心理模擬、生態模擬、繁殖遺傳、探索生成、雲端服務及所有未來功能。未經實際測試，不得宣稱平台相容或穩定性驗收通過。


## 十六、歐姆世界觀與長期生活感方向

**狀態：大方向已確認；世界歷史、地理與文明細節待逐步建構。**

### 16.1 世界定位：完整的地下文明
歐姆是一個具有成熟居民文明的廣闊地下世界，不只是荒野洞穴或單一研究設施。世界中可以有城市、村莊、聚落、交通、生活設施、文化與社會制度；同時保留廣大的自然區域，包括洞穴、地下森林、河流、湖泊、沼澤、山地及尚未探索的生態環境。

文明與自然必須並存且互相影響。城市居民的生活、研究與保育活動，應與周圍真實運作的自然生態產生合理關聯。研究站是歐姆世界中的一種生活場所，也是玩家接觸生命、居民與自然環境的重要據點。

### 16.2 長期生活感：期待、習慣、回憶、熟悉感
- **期待：** 玩家因對個體生命產生真實好奇，而期待觀察動物的活動、成長、蛻皮與行為變化；不是因任務催促。
- **習慣：** 玩家逐漸熟悉動物常出現的位置、NPC 的生活節奏、研究站不同時段的氣氛，以及環境聲音與音樂。
- **回憶：** 動物成長、重要照護事件、研究成果、NPC 人生變化及研究站改造等真實發生的事件自然留下紀錄。
- **熟悉感：** 玩家即使沒有明確目標，也能自在地看看動物、走過熟悉的場所、與居民交談，享受回到這個世界的感覺。

### 16.3 生活感設計原則
1. 不是讓玩家每天都有事情做，而是讓玩家每天都有值得期待的事。
2. 動物、NPC 與環境都有自己的生活，不以玩家上線或任務觸發作為唯一存在理由。
3. 不使用強迫每日登入、逾期懲罰、過量通知或任務壓力維持玩家活躍。
4. 長期成長、習慣、關係與回憶自然累積，不把所有日常事件都轉成成就或待辦。
5. 保留每隻動物與每位 NPC 的個體差異；動物行為必須尊重物種生物學與認知能力。
6. 生活感應該是玩家自然感受到的體驗，不應成為另一套需要玩家管理的複雜系統。
7. 內部模擬以低負擔、事件導向及重要事件紀錄支撐體驗，並服從「穩定遊玩優先於功能完整」原則。

### 16.4 待建立的背景內容
- 歐姆文明起源、歷史與重要事件。
- 地下世界地理、城市／村莊分布、交通及區域特色。
- 居民種族、文化、語言、職業與生活方式。
- 城市文明、自然生態與生命守護制度之間的關係。
- 玩家作為地上訪客的身份、來到歐姆的原因及長期生活方式。

本節確立世界觀方向與體驗判準；未列明的細節仍屬待設計，不視為已定案。相關功能也不代表已完成程式實作。


## 十七、核心體驗深入、日常管理負擔輕

**狀態：核心方向已確認；各系統的實際深度、操作介面與數值仍待分階段設計。**

### 17.1 核心體驗可以深入
以下是玩家值得投入時間的主要內容：
- **動物生態與個體觀察：** 個體差異、生活習慣、活動時間、躲藏、探索、覓食、成長、蛻皮、繁殖、健康及環境反應。所有動物行為與照護依物種真實生物學及認知能力設計。
- **動物健康與生命變化：** 透過觀察、照護紀錄及環境資訊理解生命狀態，不把動物當成收益資源，也不只用抽象數值取代行為。
- **NPC 人際關係與自主生活：** NPC 擁有自己的作息、興趣、友誼、信任、情感、煩惱、目標與重要記憶；能主動互動，也能在玩家離線時繼續生活。
- **世界生態演變：** 生物與棲地有合理的長期變化，讓探索、研究及保育有意義。
- **實習生養成：** 以學習、經驗、能力與角色故事形成長期成長，不把養成轉成繁瑣的人事考核。

### 17.2 日常管理負擔應輕
- 研究所財務以清楚、低頻、容易理解的方式呈現，避免複雜帳務與頻繁對帳。
- 人事管理不設計大量排班、薪資計算、考勤或行政表單。
- 設備維護只保留與核心照護、研究或安全直接相關且有意義的部分。
- 日常行政盡量自動化、摘要化或合併處理，避免玩家反覆點選例行工作。
- 管理介面協助玩家理解現況及做重要決策，不讓玩家成為全職行政人員。

### 17.3 設計公式
**核心體驗可以深：** 動物、生態、人物、情感、探索與生活。

**日常負擔要輕：** 財務、人事、行政、例行管理與設備操作。

挑戰應主要來自觀察、理解、照護、研究、探索與人際選擇，而非重複填表、點擊或瑣碎行政。

### 17.4 深度與操作負擔分離
- 系統內部可保有細緻資料，但玩家不必操作每個底層參數。
- 低價值重複流程應自動化、批次化或摘要化；重要且有趣的決策才交由玩家處理。
- 深度不等於每秒運算或大量即時模擬；採事件觸發、低頻結算與分階段載入。
- 所有深度系統服從「穩定遊玩優先於功能完整」；若負擔或效能成本過高，先簡化實作，必要時縮減或延後非核心功能。

本節確立體驗深度與玩家負擔的分配原則，不代表列舉系統均已實作，也不代表未定細節已經定案。


## 十八、歐姆語言多樣性與翻譯器演進

**狀態：語言多樣性的核心方向已確認；族群語言資料、翻譯器功能與學習機制待後續設計。**

### 18.1 通用語與族群語言並存
- 歐姆有一套大多數居民都能使用的通用語，方便跨族群溝通。
- 不同族群仍保留自己的語言、地方方言、語氣、發音與文化表達。
- 通用語不代表其他語言被取代；不同族群不必使用相同口頭禪或語助詞。
- 同一族群內，年齡、家庭背景、成長環境與個人習慣也會造成語言差異。

### 18.2 第一代翻譯器的辨識範圍
| 語言類型 | 第一代翻譯器表現 |
| --- | --- |
| 歐姆通用語 | 完整翻譯主要語意 |
| 常見地方方言 | 大多能翻譯，可能保留少量語氣差異 |
| 特殊族群語言 | 部分辨識，主要語意可能可翻譯 |
| 族群特色語助詞／口頭禪 | 可能保留原音，不擅自替換成近似通用語助詞 |
| 古老或失傳語言 | 可能無法翻譯，或只能辨識少量詞彙 |

例如特殊族群居民說「今天的天氣很好，吼呀～」，翻譯器可呈現已翻譯的句子並保留「吼呀～」，而不是擅自翻成「呢」或「喔」。系統須區分主要語意辨識與文化語氣理解。

### 18.3 NPC 語言個體特色
NPC 可依族群、年齡、家庭背景與個人經歷，形成不同的專屬語助詞、口頭禪、發音、說話節奏、問候方式及場合用語。語言是角色辨識與文化生活的一部分，不應只用單一搞笑詞彙代表整個族群。

### 18.4 翻譯器後續升級
第二代翻譯器可增加特殊族群語言資料庫，逐步理解語助詞的真正語氣、情緒、場合與文化含義。升級後仍可保留原音顯示，讓玩家看見語言原貌，而不是把差異全部轉換成通用語。

### 18.5 玩家熟悉與學習（延伸提案）
玩家長期與 NPC 相處後，可逐步從情境、互動與記憶理解常見表達，甚至在熟悉的場合不必完全依賴翻譯器。具體學習系統、介面與進度尚待設計，應自然融入生活，不增加每日作業或繁瑣管理。

### 18.6 技術與體驗限制
- 翻譯器是溝通輔助工具，不是語言同質化工具。
- 翻譯結果可區分完整翻譯、部分辨識與未知語句，介面保持清楚、低負擔。
- 語言資料與判斷採輕量資料及情境規則；避免大量即時 AI 運算影響手機與電腦效能。
- 本節為設計規格，不代表翻譯器、語言資料庫或語言學習功能已實作。



## 十九、隨身研究終端：開場揭示、翻譯、紀錄與個人資料庫

**狀態：開場揭示方式、設備定位、核心功能方向及資料分層原則已確認；介面、設備背景、權限、容量與實作順序待規劃。**

### 19.1 開場以實際需求揭示設備
開場不先用長篇裝備說明介紹翻譯器，而是讓玩家先抵達歐姆車站、看見地下城市，並在車站廣播及居民交談中遇到陌生語言。當玩家確實遇到溝通隔閡時，翻譯器才自動啟動並提示辨識與翻譯功能。之後玩家透過設備與登記人員溝通，前往戶政暨生物登記所，逐步認識歐姆文化、身分及姓名制度。

**開場流程：** 地熱纜車抵達車站 → 初見地下城市 → 聽見無法理解的歐姆語 → 翻譯器自動啟動 → 使用翻譯器與登記人員交流 → 前往戶政暨生物登記所。

原則：先讓玩家遇到問題，再讓玩家發現工具。具體演出與對話仍待設計。

### 19.2 設備定位
翻譯器擴展為玩家長期使用的**隨身研究終端**。翻譯是初期最重要的功能，但設備也支援生活紀錄、觀察整理、研究筆記及資料檢索。它應陪伴玩家從初抵歐姆、逐漸熟悉居民語言與文化，到長期探索和研究。

### 19.3 五項核心功能
| 功能 | 設計用途 |
| --- | --- |
| 即時翻譯 | 歐姆語與地表語言雙向翻譯；沿用族群語言、方言、語氣及原音保留規則 |
| 語音紀錄 | 在符合知情與隱私規範的前提下，保存玩家有權記錄的重要談話或研究語音 |
| 文字轉錄 | 將獲准處理的語音轉為文字，必要時保留原文、翻譯及辨識狀態 |
| 研究筆記 | 玩家主動記錄觀察、想法、心得與研究問題 |
| 資料檢索 | 查閱過去的翻譯、語音／文字紀錄、研究筆記及相關資料 |

五項功能為核心規劃方向，不要求在開場一次全部開放；可隨玩家生活與研究需求逐步介紹。

### 19.4 三層資料紀錄
必須區分下列資料，不得自動把所有設備紀錄變成正式研究成果：

1. **自動紀錄：** 在正常使用及權限允許範圍內，記錄設備辨識到的語音資訊、時間、翻譯結果與辨識狀態等。自動紀錄不代表可以秘密保存完整 NPC 對話錄音。
2. **玩家紀錄：** 玩家主動撰寫的觀察、想法、心得、發現地點與行為描述。
3. **正式研究資料：** 經玩家整理及確認，符合遊戲內研究要求後，才納入正式研究資料庫。

自動紀錄與玩家筆記可作為研究素材，但不能未經確認就視為已驗證的科學結論；應保留資料來源與確認狀態。

### 19.5 野外觀察案例
玩家發現陌生地下蛙類時，終端可協助辨識 NPC 對該物種的稱呼、保存允許記錄的叫聲、記下時間與地點，並讓玩家補充觀察行為。資料先成為可回顧的觀察紀錄；玩家日後可在研究站整理，再決定是否納入正式研究資料。適當資料可與研究日誌、博物館及《歐姆生活紀錄》連動，具體欄位與流程待設計。

### 19.6 NPC 對話與隱私
- 即時翻譯、保存文字轉錄、保存完整音訊、提交或公開研究資料，是不同用途，需有清楚的知情、同意與使用範圍。
- 不得預設玩家能秘密錄下 NPC 對話，也不得因持有終端就取得 NPC 私人談話或個人資料的存取權。
- NPC 是否同意分享或保存對話，依個性、關係、情境與隱私觀決定。
- 具體同意提示、保存期限、刪除方式與例外情境待後續規劃；介面須清楚且低負擔。

### 19.7 效能、儲存與跨平台原則
- 手機及電腦均需能穩定使用；錄音、轉錄、索引與整理不可阻塞主要遊戲流程。
- 採輕量資料結構、分批處理及按需載入；避免大量原始音訊長期保存造成效能與儲存負擔。
- 提供清楚的資料來源、保存狀態、同意及刪除資訊。
- 若完整語音功能造成過高效能、隱私或開發成本，優先保留核心翻譯與研究筆記，簡化或延後進階功能，遵守穩定遊玩優先原則。

本節為設計規格，不代表翻譯器、錄音、轉錄、資料庫或跨平台功能已完成實作。


## 二十、玩家雙重姓名與跨世界郵件身分規則

**狀態：雙重姓名的情境使用原則已確認；姓名資料欄位、郵件介面及個別劇情待設計。**

### 20.1 兩套姓名代表兩種身分
- **歐姆正式姓名：** 玩家在歐姆登記、生活、工作、建立人際關係及使用歐姆官方文件時的身分。
- **地表真實姓名：** 玩家與地表原本世界、過去生活及地表人際網絡的連結。
- 兩套姓名必須獨立保存，不因郵件收件稱呼、包裹標籤、NPC 對話或介面顯示而互相覆蓋。
- 地表姓名與歐姆姓名的對應屬玩家個人身分資訊；NPC 只有在合理劇情、正式必要程序或玩家主動分享後，才能知道地表姓名。

### 20.2 依情境選擇姓名

| 情境 | 使用姓名 |
| --- | --- |
| 歐姆居民日常稱呼 | 歐姆姓名的日常稱呼形式 |
| 歐姆官方文件 | 歐姆正式姓名 |
| NPC 好友稱呼 | 歐姆姓名、日常稱呼或關係專屬暱稱 |

| 地表聯絡人 Amy 的私人信件 | 依熟悉程度使用地表姓名或親近稱呼 |

### 20.3 郵件與包裹來源規則
1. 地表機構寄送的包裹、正式信件及研究報告，預設以地表真實姓名作為收件人。
2. 歐姆本地機構寄送的文件、包裹及正式通知，預設以歐姆正式姓名作為收件人。
3. 系統依寄件來源／所屬世界決定使用哪套姓名，而不是依玩家目前身處哪個世界或最近使用哪套姓名決定。
4. NPC 私人信件依寄件者個性、關係與熟悉程度選擇稱呼；Amy 可自然使用正式地表姓名或較親近的稱呼。
5. 收件標籤與信件稱呼只是顯示方式，不得回寫或修改玩家的姓名資料。
6. 郵件系統應自動判斷來源並套用正確姓名，不增加繁瑣的手動收件人管理。

### 20.4 第一次收到地表姓名包裹
玩家第一次在歐姆收到以地表真實姓名寄送的包裹時，可由老馬克或其他合適 NPC 注意到包裹上的名字與歐姆登記姓名不同，並自然詢問這是否為玩家在地表使用的姓名。此情境只在第一次符合條件時觸發，不應每次收到地表包裹都重複播放。

這個小事件用來溫和呈現玩家與地表世界仍有連結，不應變成強迫揭露身分或引發不必要的身分危機。具體 NPC、對白與玩家回應仍待劇情設計。

### 20.5 隱私與內容設計限制
- 不可讓一般歐姆居民無故知道玩家地表真實姓名。
- 不同 NPC 是否知道地表姓名，需有明確的知情來源與劇情依據。
- 玩家提供的「陳子安研究員／陳子安」是情境示例，未經確認不視為正式角色姓名。
- 後續需設計姓名資料欄位、可見權限、地表聯絡人資料及跨世界郵件來源分類。

本節為正式設計規格，不代表雙重姓名、郵件判斷或首次包裹劇情已完成程式實作。


## 二十一、地表與歐姆語言獨立性及姓名文化

**狀態：兩個世界的語言文化獨立原則，以及「歐姆・歐姆」稀有姓名規則已確認；語言與命名資料待逐步建立。**

### 21.1 兩個世界的語言各自發展
- 地表語言與歐姆本地語言是各自發展的語言系統，沒有必然的共同詞源、語義或歷史關聯。
- 兩邊偶然出現相同或相似的字詞，不代表它們有共同來源，也不能預設地表詞彙指向歐姆地下國。
- 歐姆是擁有自身語言、歷史與文化的獨立地下文明，不是地表世界的語言延伸。
- 歐姆內部仍保留既有設定：有大多數居民可使用的通用語，同時存在地方方言、族群語言與個體語言特色。此規則不會抹除歐姆內部的語言多樣性。

### 21.2 地表姓名與歐姆姓名各自獨立
- 玩家地表真實姓名依地表文化與命名習慣建立；即使包含「歐姆」字詞或相同讀音，也完全合理，不必避開、替換或特別解釋。
- 玩家歐姆姓名依地下文化、歐姆語言及當地命名習慣建立。
- 兩套姓名各自保存、各自使用，不因字面相同而推定文化或語義關聯，也不互相限制或覆蓋。
- 「歐姆」是地下國在歐姆語言中的國名；地表語言出現同樣的字詞，不代表該詞就是地下國名稱。

### 21.3 「歐姆・歐姆」稀有姓名彩蛋
- 歐姆地下姓名資料庫可以收錄「歐姆」作為姓氏。
- 一般名字（given name）資料庫不收錄「歐姆」作為一般名字。
- 「歐姆・歐姆」保留為獨立的稀有完整姓名紀錄，不透過一般姓氏與名字資料庫的隨機組合生成。
- 此姓名是罕見姓名彩蛋，不附帶特殊能力、地位、經濟優勢或玩法加成。
- 上述限制只適用於歐姆地下姓名資料庫，不限制地表姓名；地表文化中仍可自然出現相同字詞或姓名。

### 21.4 待建立的文化資料
- 歐姆語言的語音、文字、詞彙、語法及歷史演變。
- 歐姆不同族群、地區與家庭的姓名文化及命名規則。
- 地表各語言與姓名文化的背景資料。
- 「歐姆」姓氏在歐姆社會中的來源、使用情況與稀有程度。
- 「歐姆・歐姆」完整姓名紀錄的資料欄位與出現方式。

本節為世界觀及姓名制度規格，不代表完整語言或姓名生成系統已完成實作。


## 二十二、「語言隔閡與文化適應」開場設定

**狀態：開場設計原則已確認；具體演出、翻譯器初始能力、教學對白與語言學習進度待細化。**

### 22.1 抵達之前
玩家來自地表阿斯特拉生態研究會（Astraea Institute of Ecology）。出發前收到研究任務、研究站資料及必要生活準備資訊，知道目的地是地下研究區域，當地有居民與獨特生態；不必預先知道地下國完整歷史、文化或正式國名「歐姆」。研究會可提供有限語言資料或基礎翻譯設備，但不代表玩家熟悉當地語言文化。準備資料以實用資訊為主。

2. **玩家理解層：** 玩家透過研究會資料、翻譯設備、辦事情境與長期生活接觸理解歐姆居民，理解程度不等於瞬間精通。
3. **遊戲顯示層：** 依玩家介面語言呈現已理解或已翻譯內容；特殊劇情可保留未理解文字、原音或翻譯不確定性。

### 22.5 語言體驗原則
- 玩家抵達時不完全精通歐姆語，但語言隔閡不能阻礙基本遊戲。

- 地方俚語、族群語助詞與文化暗示可透過互動及長期相處逐漸理解；翻譯器不抹平文化差異。
- 教學融入登記、居民互動、博物館與日常生活，不設強制語言課或阻擋核心玩法的關卡。
- 玩家來歐姆是為了生活與研究，不是來上語言課；語言不應成為繁重待辦。

### 22.7 待細化
研究會提供的語言資料與設備；翻譯器初始辨識程度及錯譯表現；車站廣播、標誌與首次看見國名的演出；登記所流程與對白；歐姆本地文字及轉寫規則；語言熟悉度是否需要可見數值（優先自然呈現，避免增加管理負擔）。

## 二十三、V26.0 NPC 自主生活、情緒關係與咖啡館社交系統

**狀態：** 核心理念及系統方向納入規劃；候選角色、數值平衡、場景配置、刷新頻率與實作模組尚待確認。此節為規格，不代表已完成程式實作。

### 23.1 核心理念
NPC 是有自己生活、工作、朋友、興趣、回憶與煩惱的自主個體。玩家可參與、旁觀或不介入。禁止以每日登入、逾期懲罰、社交維護清單或 NPC 情緒責任迫使玩家遊玩。故事可在玩家不在場時發生；玩家不是所有人的救世主。

### 23.2 NPC 生活與社交
NPC 擁有個性、職業、行程、偏好、目標、背景、秘密、壓力調適方式及人際網絡。可在咖啡館、博物館、植物園、研究機構、商店、廣場、溫泉、居住區與街道等地點活動。NPC 彼此可交談、交友、合作、交換資訊、誤會、爭執、和解、參加活動或在適合情況下建立特殊關係。互動不必全部讓玩家看見。

### 23.3 模擬效能原則
沿用重要事件模擬、低頻結算、事件觸發與摘要記錄；不逐分鐘模擬所有 NPC，不持續執行完整 AI。只優先保存影響人生、關係、心情、工作研究或玩家後續體驗的重要事件。離線不得成為玩家或 NPC 的不合理懲罰。若效能受影響，先簡化、延後或停用進階模擬，穩定遊玩優先。

### 23.4 好感、信任、心情與心理特質
好感度、信任度、心情值是三項獨立資料：好感表示親近程度、信任表示信賴程度、心情表示當下情緒。心情值暫定 0–100，區間參考為 0–19 非常低落、20–39 不愉快、40–59 平靜、60–79 愉快、80–100 非常愉快；此數值尚待平衡，也不代表必須向玩家顯示。

心情不得與人格或心理韌性混為一談。樂觀／悲觀、抗壓性、情緒恢復力、情緒敏感度、自我調適能力仍為獨立維度。不同 NPC 有不同壓力表現及恢復方式，可選擇透露、求助或保留隱私。心情可影響語氣、互動意願、邀請、行為及事件，但不能變成玩家待辦；昂貴禮物不能通用地修復情緒。

### 23.5 關係階段、稱呼與戀愛
好感階段暫定參考：0–19 陌生、20–49 熟悉、50–79 親近、80–99 特別羈絆；戀人須透過獨立關係事件成立，不能只靠數值自動發生。不同 NPC 可有個別門檻；不是所有 NPC 都能戀愛。告白失敗、重複告白與分手依個性、信任及過往事件處理。

延續初期以「玩家姓氏＋研究員」等正式稱呼為主，親近稱呼與戀人暱稱由 NPC 依關係自然形成；關係破裂可停止使用親密暱稱。稱呼不覆寫雙重姓名資料。

### 23.6 記憶、相簿、日記與音樂
只保存有意義的事件，不記錄所有日常對話。延續 NPC 個人記憶、私人照片收藏、戀人共同相冊與日記的既有隱私規則；照片必須來自遊戲中真實發生的事件，分手不會由系統直接抹除共同經歷。部分 NPC 可有個人主題音樂，透過故事、羈絆、節日或重要事件解鎖，並在適當情境連結回憶。

### 23.7 咖啡館
咖啡館是重要委託交流與日常社交場所，但不是唯一任務來源。五區域為初步提案：
- 委託公告板：公開生活與研究委託。
- 窗邊座位：偶遇、聚會、私人談話與街景。
- 咖啡櫃檯：飲料、店員互動及城邦消息。
- 私人座位：個人故事、羈絆與約會。
- 活動空間：節慶、演奏、聚會與特殊劇情。
NPC 依個人行程造訪；有固定常客，也有偶爾出現者。玩家不必每天巡查。

### 23.8 動態委託
委託來源包括公開公告板、NPC 個人委託與偶發事件；研究機構、博物館、商店等也可提供專屬委託。類型包括寄養、尋物、採集、生態觀察、生活協助、動物照護、研究學術與節慶活動。可有固定劇情、條件觸發、一般週期性及特殊事件委託，但刷新頻率待平衡，不得造成每日必做或錯過懲罰。

拒絕委託本身不降低關係；只有主動承諾後違背重要承諾，且符合事件脈絡，才可能影響關係。委託應可合理協商、延期或取消。

### 23.9 動物寄養
流程為需求提出、確認物種年齡健康及照護需求、檢查獨立空間與設備、接受並記錄、照護觀察、期滿歸還。寄養動物不是玩家財產，不可出售、繁殖、放生或轉移所有權。健康問題須提供明確警示及合理處理時間，不可毫無預警死亡；遵守物種需求與動物福利。

### 23.10 新增 NPC 候選
瑪莉亞（咖啡館經營者）、伊蓮（植物學家）、奧斯卡（地質研究員）、諾菈（生物醫療師）、里昂（街頭音樂家）、芙蕾雅（博物館與檔案管理員）目前均為候選概念，尚未定案。正式建立時須補完整姓名，遵守姓氏、名字分開儲存及姓名文化來源等既有制度。

### 23.11 程式架構方向
NPC 個性、行程、社交、關係、心情、記憶、命名、戀愛、對話、事件、音樂；咖啡館社交與公告板；委託生成、條件、管理、獎勵；動物寄養等是功能責任分組，不代表必須各建一個檔案。實作應依現有架構整併為少量、清楚、可測試的模組，避免過度拆分。

### 23.12 待確認
候選 NPC 正式姓名與背景、NPC 模擬頻率及社交變化、咖啡館配置、羈絆與戀愛資格、個人故事及音樂、心情與好感數值平衡、委託刷新及獎勵、寄養期限與健康事件流程。


## 二十四、NPC 陣容擴充與彼此獨立生活（核心原則）

**狀態：** NPC 彼此擁有獨立生活與關係，正式列為核心系統原則；新增角色及陣容數量仍為候選規劃。

### 24.3 NPC 彼此的生活與關係是核心系統
NPC 不只與玩家建立關係，也彼此擁有獨立的人際網絡、生活安排、共同經歷與關係變化。這不是玩家好感度的附屬功能，也不需要玩家撮合或在場。

- 關係依共同興趣、工作往來、生活地點、價值觀、過往經歷與個性合理形成。
- NPC 可自行約見、交談、合作、分享興趣、交換資訊、誤會、爭執、和解或逐漸疏遠。
- 關係變化需有可理解的經歷與原因，不以純隨機任意改變；也不必每段關係都戲劇化。
- 玩家可能偶然看到 NPC 一起喝咖啡、相約植物園，或察覺近期互動改變；即使玩家未目擊，事件仍可在背景合理發生。
- NPC 不為了玩家到場才開始互動，也不會把所有私人關係主動報告玩家。
- 私人談話與秘密仍受個體隱私及分享意願限制。
- NPC 關係可成為後續行程、對話、活動、記憶與事件的背景，但不得大量轉化成玩家待辦事項。

### 24.4 陣容規模初步目標
- 核心劇情 NPC：5–8 位。
- 地下城邦生活 NPC：10–15 位。
- 研究與生態專業 NPC：5–8 位。
- 偶遇及短篇故事 NPC：持續擴充。

分類可能重疊，一位角色可同時屬於核心劇情與專業角色，因此不可直接相加視為總人口。數量是規劃參考，不是硬性上限或一次完成的清單。應先建立少量有辨識度、關係可信的角色，再依城邦規模、接觸密度、內容品質、製作成本與效能逐步擴充。

### 24.5 特殊 NPC 故事原則
部分 NPC 表面日常如常，實際有自己的壓力、牽掛或未說出口的經歷；故事可透過細微行為、對話與再次造訪逐漸理解。但安靜、獨處或遲到不必然代表創傷或求助。部分 NPC 只是喜歡獨處；不是每個困擾都要變成任務或玩家介入。NPC 有權保留私事，玩家不追問也是尊重。角色開朗、溫柔、寡言或幽默可以是真實性格，不必都被設定成悲傷的掩飾。

### 24.6 效能與內容品質
NPC 彼此生活沿用重要事件模擬、低頻結算、事件摘要與必要狀態更新；不模擬所有人的每一秒。新增 NPC 數量不得凌駕穩定性、角色品質與玩家可理解程度。若效能或內容維護負擔增加，優先縮小同時模擬範圍、合併功能、延後角色或減少陣容，而不是犧牲手機與桌面遊玩穩定性。


## 二十五、V26.0 動態任務與 NPC 委託系統

**狀態：** 納入整合基礎；數值、刷新頻率、期限及獎勵待開發平衡，尚未實作。

### 25.1 核心定位
任務是地下城邦生活的一部分，而非每日待辦機器。玩家可主動查看公告板、接受 NPC 親自委託，或從探索與偶遇中發現需求。玩家可拒絕、協商、延期或取消，不必承接所有事情。

### 25.2 七大任務類型
1. 動物寄養。
2. 尋物與收集。
3. 生態觀察。
4. 生活協助。
5. 動物照護。
6. 研究與學術。
7. 節日與特殊事件。

### 25.3 任務來源與生成
任務來源分為固定劇情、條件式動態任務及日常一般委託。生成前先檢查 NPC 需求、個性、忙碌程度、玩家條件、動物狀態、空間與必要資源；不符合條件時不生成無法完成的委託。NPC 心情低落不代表必然求助，信任不足者可能不願交付重要物品或動物。

公告板、NPC 主動委託、探索偶遇三種入口共用任務狀態與條件管理，避免重複任務或彼此衝突。不是所有被發現的生活事件都必須變成正式任務。

### 25.4 動物寄養
寄養前確認物種、個體、年齡、健康、飲食、溫濕度、環境及預計期間，並檢查玩家是否有合適的獨立空間。接收時記錄原飼主、個體資料、健康狀態與照護需求。寄養期間可出現適應、拒食、環境偏差、疾病徵兆或原飼主延遲返程等事件，提供合理觀察、改善與醫療求助窗口，不可無預警造成死亡。

寄養動物不屬於玩家：不可販售、擅自繁殖、放生、轉移所有權或任意永久留下；原則上歸還原飼主，延期須有合理原因與協調。動物安全與照護品質優先於任務成功率、天數及報酬。

### 25.5 尋物與研究
尋物可透過線索、訪談、場景觀察、辨識及研究完成，不只是撿取指定物品。相似但錯誤的物種或材料應能被辨識；玩家可查百科、請教專家或自行研究。研究紀錄需保留來源、觀察條件與確認狀態；觀察不自動等於已驗證結論。動物研究須尊重物種習性與福利。

### 25.6 NPC 關係與任務記憶
拒絕委託本身不自動降低好感或信任。玩家接受後違背重要承諾，才依嚴重程度、溝通及 NPC 個性產生合理影響。任務完成、重要協助、承諾履行或違背可寫入 NPC 重要記憶，影響後續對話與故事。NPC 心情、信任與忙碌程度可影響是否提出委託，但不由單一數值決定。

### 25.7 獎勵、後續故事與期限
獎勵可包括貨幣、物品、設備、植物、生態資料、百科紀錄、研究素材、關係變化、紀念物、個人故事及內容解鎖；依實際成果與照護品質評估。任務可延伸成後續故事，例如寄養結束後原飼主接回動物並分享近況，或委託材料轉交另一位研究者，形成 NPC 之間的合作。

期限依任務性質設定；普通尋物可寬鬆，研究可有進度，寄養以預計返程為基準並可合理延期，醫療協助依風險安排優先度。節慶活動不得以錯過就懲罰玩家。困難時可延期、協商、取消或調整；失敗後果不一律扣錢，動物安全優先。

### 25.8 建議模組方向
`quest-generation-system.js`、`quest-condition-system.js`、`quest-management-system.js`、`quest-reward-system.js`、`foster-care-system.js`、`item-search-system.js`、`ecology-commission-system.js`。以上為功能邊界建議，不強制一功能一檔案；應依既有架構共用資料與狀態，避免重複模擬。

### 25.9 效能與慢生活保護
任務採條件檢查、低頻或事件觸發，不持續掃描所有 NPC、動物與物品。玩家離線不得因未登入受到不合理懲罰，尤其不得因任務逾期使寄養動物無預警死亡。若生成或跨系統連動造成負擔，先縮小範圍、降低頻率、簡化條件或延後進階類型；仍影響穩定時暫緩或移除複雜功能。

### 25.10 待平衡
任務數量、刷新頻率、類型比重、獎勵、期限、信任條件、寄養評估及實際模組邊界待後續開發與遊玩測試。本節為整合規格，並非已完成實作。


## 二十六、V26.0 NPC 情感、心情與記憶系統規格

**狀態：** 納入整合基礎；數值、個別 NPC 門檻及事件機率待平衡，尚未實作。

### 26.1 三項獨立資料
好感度代表親近程度；信任度代表是否相信玩家；心情值代表當下情緒。三者分開運作，不互相取代。NPC 可喜歡玩家但因自身生活不順而心情低落。

### 26.2 好感階段與稱呼
初步好感區間：陌生 0–19、熟識 20–49、親近 50–79、特殊羈絆 80–99；戀人為獨立狀態，必須透過正式告白事件成立。每位 NPC 可有個別門檻。玩家建立角色時輸入姓氏與名字；NPC 初期可稱「姓氏＋研究員」，之後依個別關係使用本名或親密稱呼。專屬暱稱由 NPC 自然決定；關係降級或分手可改回正式稱呼，不覆寫玩家地表／歐姆雙重姓名資料。

### 26.3 好感與信任變化
長期未互動、違背承諾、欺騙、做出 NPC 厭惡之事、傷害其重視的生物或反覆忽略重要事件，可能影響關係。衰減速度、厭惡事項及反應依個性與事件，不採全 NPC 相同規則，也不把玩家日常生活變成登入壓力。

### 26.4 心情值
心情初步採 0–100：0–19 非常低落、20–39 不開心、40–59 普通、60–79 愉快、80–100 非常開心。心情不在每日午夜自動重設，會受玩家互動、NPC 自身生活、工作研究、其他 NPC 關係、城邦事件、節慶、季節環境與個性影響。情緒變化與恢復方式依個體而異。

心情可影響互動意願、對話、獨處、分享、邀約與驚喜，但不應變成固定腳本。NPC 心情低落不代表不喜歡玩家；送禮還需考慮關係、信任、個性、經濟與禮物準備，不能用昂貴禮物直接控制情緒。

### 26.5 情緒事件
可有獨處、情緒來信、安靜陪伴、心情好轉及特殊感謝。玩家可以傾聽、陪伴、協助或尊重獨處，不必解決 NPC 的問題。NPC 是否透露心事與接受陪伴依個性、信任、情境及隱私決定。

### 26.6 告白與關係破裂
告白考慮好感、信任、個人故事、NPC 個性、當前情緒及劇情狀態。失敗可能造成好感下降、親密互動暫停、尷尬或疏遠期；重新告白條件依個體與後續互動。戀人可能因重大衝突分手；共同回憶不會被系統直接刪除，保留、封存或回顧依 NPC 個性與事件決定。並非所有 NPC 都必須可戀愛。

### 26.7 NPC 記憶
記錄重要事件而非所有日常對話：初次相遇、初次互動、第一次主動聊天、第一次使用名字、第一次聽見專屬歌曲、承諾履行或違背、共同活動、告白交往分手、第一次使用專屬暱稱、低潮時受到陪伴等。記憶可觸發後續對話、紀念日及個人劇情。

### 26.8 專屬歌曲與生活週期
NPC 可有個人主題歌曲，依故事、演奏、羈絆或紀念事件解鎖，並與記憶連動；不要求每位 NPC 都有歌曲。NPC 可有工作時間、休息日、研究進度、個人節日、社交活動與壓力恢復週期，以重要事件、行程時段與低頻結算模擬，不進行所有 NPC 每日複雜運算。

### 26.9 建議功能責任
`npc-relationship-system.js`、`npc-personality-system.js`、`npc-mood-system.js`、`npc-memory-vault.js`、`npc-naming-system.js`、`npc-romance-system.js`、`npc-event-system.js`、`npc-gift-system.js`、`npc-dialogue-system.js`、`npc-music-system.js`。這些是功能責任建議，不強制一功能一檔案；正式開發前先檢查既有架構並合理整併。玩家可見文字由語言系統管理，支援繁體中文及英文。

### 26.10 待平衡與穩定性
好感及心情門檻、個別 NPC 條件、衰減速度、情緒事件機率、告白後果與送禮條件待後續測試。與 NPC 自主生活、彼此關係、隱私、咖啡館及動態委託共同適用。穩定遊玩優先，採事件觸發、低頻結算與必要記憶；負擔過高時簡化或延後非核心功能。


## 二十七、V26.0 NPC 心情與情緒反應系統

**狀態：** 納入整合基礎；數值、事件權重及個別 NPC 反應待平衡，尚未實作。

### 27.1 系統定位
NPC 心情與情緒反應是既有 NPC 情感、心情與記憶系統中的獨立子系統，不另建平行關係或記憶資料。明確區分好感度（長期親近）、信任度（可靠性與信賴）、心情值（當下情緒）及心理特質（樂觀／悲觀、抗壓性、情緒恢復力、敏感度、自我調適能力）。

### 27.2 心情狀態與來源
心情暫定 0–100：0–19 非常低落、20–39 不開心、40–59 普通、60–79 愉快、80–100 非常開心。區間僅供參考，待平衡；不每日午夜重設，也不要求介面顯示精確數字。來源包含玩家互動、玩家負面行為、NPC 自身生活、世界環境與個人特質。

### 27.3 行為與禮物
心情可影響對話、互動意願、獨處、分享、邀約、活動與送禮，但不是固定腳本。送禮同時考慮心情、好感、信任、關係階段、個性、經濟狀況、物品準備及過往紀錄。暫時不送禮不代表關係惡化；昂貴禮物不能成為通用情緒修復工具。

### 27.4 情緒事件與個人調適
可能出現獨處、情緒來信、安靜陪伴、逐漸好轉及特殊感謝等事件；NPC 可選擇透露部分心事或保留隱私。玩家可陪伴、傾聽、協助或給予空間，不必解決每個問題。調適方式依個性、心理特質、生活習慣與經歷而異。

### 27.5 生活週期、記憶與效能
NPC 可有休息日、工作疲憊、研究前緊張、節日期待或特定日期回憶等節奏，以行程、重要事件與低頻狀態更新呈現。重要情緒事件寫入既有 NPC 記憶庫；心情恢復不刪除回憶。沿用事件觸發、低頻結算及重要事件優先，不執行所有 NPC 逐分鐘模擬。

### 27.6 待平衡
心情區間、變化幅度、事件權重、恢復節奏、個別 NPC 反應與送禮判定待後續測試；本節為規格，並非已完成程式實作。


## 二十八、V25.0 第一章：遊戲開局與初始生物選擇

**狀態：** 正式納入；本章取代舊版以救援事件取得第一隻寵物的開局安排。此為正式劇情與玩法規格，尚未代表程式實作完成。

### 28.1 開局背景與教育定位

玩家以阿斯特拉研究院派駐人員身分前往地下觀測站，準備展開生態研究生活。正式開始研究工作前，玩家先前往地底爬蟲博物館，由館長老馬克（Mark）接待。

老馬克透過博物館導覽介紹歐姆地下世界的爬蟲與兩棲動物文化、物種知識、生命特徵及生活習性。這段導覽同時承擔新手教學：先讓玩家理解觀察、環境需求與生命照護的重要性，再讓玩家選擇第一個研究及照護對象。

開局不再透過救援事件直接交付第一隻寵物；改以博物館教育、物種認識與玩家自主選擇建立第一段照護關係。

### 28.2 老馬克（Mark）的正式角色定位

- 正式職務：爬蟲博物館館長。
- 負責博物館日常管理及館藏維護。
- 介紹爬蟲與兩棲動物知識、物種歷史及生態習性。
- 引導玩家認識不同物種的生活需求與照護觀念。
- 提供博物館研究、物種觀察及收藏相關任務。
- 隨玩家與老馬克的關係進展，可逐步解鎖特殊館藏、深入知識及個人劇情。
- 老馬克不再擔任爬蟲商店老闆；爬蟲商店的經營者是另一位尚待安排的角色。

### 28.3 初始生物三選一

玩家完成博物館導覽與初始物種介紹後，從以下三種生物中選擇第一隻研究及照護對象：

1. **西部豬鼻蛇（Western Hognose Snake）**
   - 具有挖掘底材及探索地下空間的行為。
   - 新手教學可帶出底材深度、躲藏環境及物種適配。
2. **黃金角蛙（Golden Pacman Frog）**
   - 具有伏擊型捕食習性。
   - 新手教學可帶出濕度、水分管理及兩棲動物照護需求。
3. **豹紋守宮（Leopard Gecko）**
   - 會探索周邊環境並使用適當物件與躲藏處。
   - 新手教學可帶出地表型爬蟲的溫度梯度、躲藏處及環境配置。

上述介紹是教學切入點，不代表完整物種照護規格；正式照護參數仍須依可靠物種資料建立，不能只憑開局簡介決定。

### 28.4 選擇後的共通規則

- 三種初始候選物種都能在後續遊戲中取得，不因開局選擇而永久鎖定其他物種。
- 初始選擇主要影響開局體驗、第一個生態箱配置與初期教學內容。
- 每隻生物均建立獨立個體資料，包括個體差異、基因、性格及行為；不得把同物種個體視為完全相同。
- 玩家選擇完成後前往地下研究站，開始配置第一個生態箱並學習環境設備。
- 初始身分不會免除物種照護責任；所有生物仍須依各自需求配置環境、飲食及照護方式。
- 舊版「初始生物固定為豬鼻蛇布丁」不再是所有新玩家共通的開局設定。若保留「布丁」作為示例或既有測試資料，必須清楚標示為特定個體／測試內容，不得預設所有玩家都選到豬鼻蛇或同一個體。

### 28.5 正式開局流程

1. **研究院派駐：** 玩家抵達地下觀測站，確認研究員身分及派駐安排。
2. **參觀爬蟲博物館：** 老馬克接待玩家，介紹地下世界爬蟲與兩棲動物文化。
3. **初始物種介紹：** 老馬克介紹西部豬鼻蛇、黃金角蛙及豹紋守宮的特徵與照護重點。
4. **選擇第一隻生物：** 玩家自主選擇，建立第一份個體紀錄。
5. **前往地下研究站：** 開始配置第一個生態箱、認識環境設備及基本操作。
6. **正式開始研究生活：** 開啟動物照護、觀察、研究、探索及 NPC 互動等核心玩法。

### 28.6 核心設計原則與待實作事項

本次開局修訂的核心是「先理解生命，再開始照護生命」。玩家不是因偶發救援事件而被動取得寵物，而是在獲得基本知識後，依自己的興趣選擇第一個生命。

實作前仍需規劃博物館場景與導覽節奏、老馬克對話、多物種教學差異、三選一介面、個體生成與命名、第一個生態箱初始化，以及選擇資料的存檔相容性。開局流程需與現有新遊戲初始化、起始物種設定及存檔系統整合，不可另建互相衝突的初始化流程。

本章為 V25.0 正式規格，尚未代表博物館、劇情、選擇介面或三種初始生物已完成程式實作與跨平台測試。

### 30.1 保留前任研究員的舊生態箱：新手生態教學場景

**正式決策：** 保留研究站原有舊生態箱，作為整個遊戲最初的生態教學場景。它不是直接贈送給玩家的裝飾物，也不是開局危機事件。

#### 舊箱背景
- 舊箱由前任研究員留下，玩家接手研究站時已經運作一段時間。
- 箱內白跳蟲與球鼠婦已建立穩定繁衍的族群。
- 玩家可以先觀察既有生態，再逐步學習底材、濕度、微氣候、分解者與生態循環。
- 舊箱初始狀態應是穩定、可供觀察與學習的環境，不得一開始就要求玩家搶救或承擔未被交代的危機。
- 舊箱與玩家後續建立的寵物生態箱是不同設施；玩家仍須為自己選擇的初始動物建立符合物種需求的獨立環境。

#### 新手教學階段
1. 認識舊生態箱及前任研究員留下的觀察紀錄。
2. 觀察白跳蟲與球鼠婦，理解牠們在底材分解及生態循環中的角色。
3. 認識底材組成、濕度梯度、躲藏處與局部微氣候。
4. 使用微觀觀察工具觀察小型生物及底材中的活動；觀察工具的介面與視覺實作仍依效能評估。
5. 學習日常維護與生態平衡，不把所有生態變化都設計成必須立即修正的警報。
6. 認識清潔生物與不同寵物生態箱的關係，理解不能把同一種底材或清潔生物無條件套用到所有物種。

#### 底材移動與族群分流教學
- 玩家可學習使用小鏟、容器等工具，連同適量潮濕底材、落葉或躲藏物，將部分白跳蟲與球鼠婦移至適合的新環境。
- 白跳蟲體型微小，教學以轉移少量含有族群的適當底材為主，不要求玩家逐隻捕捉。
- 球鼠婦可輕柔移動個體，也可連同落葉、腐木或底材一起轉移；幼體可能藏在底材中，不要求一次全部找出。
- 轉移操作須避免底材乾燥、個體擠壓及不必要的翻動；濕度與底材條件應依實際物種及新環境調整。
- **不一次搬空原族群：** 舊箱保留足夠的白跳蟲與球鼠婦族群，讓原有觀察箱繼續運作；玩家只移出適量個體與底材，建立新箱中的族群。
- 轉移成功與否應依新箱的物種適配、底材、濕度及環境條件判定，不應只靠點擊一次就保證成功。
- 白跳蟲與球鼠婦並非所有動物生態箱都必須加入；實際適用性須依寵物物種、底材、溫濕度與管理方式判斷，不能把清潔生物當成通用裝飾或萬能清潔工具。

### 30.2 合併為「歐姆戶政暨生物登記所」

**正式名稱：** 歐姆戶政暨生物登記所（Ohm Civil & Biological Registry Office）。

**正式決策：** 居民身分／姓名登記與生物身分登記由同一公共機構管理，內部區分不同業務部門；玩家不需要為同一套開局身分流程往返兩棟建築。

#### 部門一：居民戶政登記
- 玩家初抵歐姆時的身分建立與登記。
- 歐姆姓氏、名字、完整姓名及姓名文化資料。
- 地表身分與歐姆身分的雙重姓名紀錄及資料保密。
- 依世界觀設定處理特殊身分與「無性別外交特赦協定」相關事項；協定的正式條文、適用範圍及劇情說明仍待細化，不得自行擴寫成未確認的法律效果。
- 官方文件使用正式歐姆姓名；地表研究會文件依既有雙重姓名規則使用地表姓名。

#### 部門二：生物身分登記
- 爬蟲與兩棲動物個體資料及識別編號。
- 物種、個體特徵、暱稱、基因型／Morph（適用時）、來源及保育身分。
- 飼養負責人、照護責任及必要的健康／觀察紀錄。
- 晶片或其他實體識別標章依物種大小、福利及實際適用性決定，不可一律要求所有物種植入晶片。
- 特殊、稀有或受保護物種依規定辦理強制登記及必要許可。

#### 一般寵物登記與開局教學的關係
既有分級登記制度繼續有效：一般寵物原則上鼓勵登記；特殊、稀有或受保護物種依規定必須登記。開局安排初始生物的正式登記櫃檯流程，是為了讓玩家學習個體識別與照護資料，不代表所有一般寵物在世界法律中都一律強制登記。

#### V25.2 正式開局流程
1. 玩家搭乘地熱纜車抵達歐姆，經歷陌生語言與翻譯器啟動。
2. 前往歐姆戶政暨生物登記所，完成玩家身分與歐姆姓名登記。
3. 前往爬蟲博物館，由館長老馬克導覽，認識物種、文化及生命照護。
4. 從西部豬鼻蛇、黃金角蛙、豹紋守宮三種初始生物中選擇一種。
5. 返回同一座歐姆戶政暨生物登記所，建立初始生物個體資料並完成開局教學所需的登記。
6. 前往地下研究站，接手前任研究員留下的舊生態觀察箱。
7. 先觀察舊箱，再學習微觀觀察、底材、濕度、生態循環及清潔生物轉移；依選擇的寵物物種另行建立自己的第一個寵物生態箱。
8. 完成基礎教學後，正式開始研究站生活與後續自由玩法。

### 30.3 三層社會認同系統（Triple Social Recognition System）

**正式決策：** 歐姆城邦信任度、NPC 個別好感度、阿斯特拉科研聲望不再被設計成完全互不相干的數值；三者各自代表不同社會關係，並可在具備合理因果時互相影響。

#### 三個核心維度
1. **歐姆城邦信任度（Civic Trust）—群體／公共關係**
   - 代表歐姆城邦居民、社區及行政機構對玩家的整體公共認同與信賴。
   - 可影響居民整體態度、公共活動、部分公共設施、保育制度參與及特定社區事件。
   - 不代表每位居民或 NPC 都會個別信任玩家，也不取代 NPC 私人關係。

2. **NPC 個別好感度（Personal Affection）—個人情感關係**
   - 每位 NPC 各自保存，代表該 NPC 對玩家的親近程度。
   - 可影響個人對話、稱呼、故事、特殊互動、禮物、羈絆及戀愛事件。
   - 不會因城邦信任度上升就讓所有 NPC 同步增加好感；只有實際影響該 NPC 的事件才可能改變其個別關係。

3. **阿斯特拉科研聲望（Academic Prestige）—學術／研究關係**
   - 代表阿斯特拉研究院及相關學術合作網絡對玩家研究成果的評價。
   - 以實際研究紀錄、方法品質、資料可信度、報告、研究貢獻及合作成果為基礎。
   - 可影響高階研究設備、科研資源、學術合作、研究課題與相關津貼等機會。
   - 科研聲望不等於研究能力本身，也不能取代真實研究資料與成果。

#### 與既有 NPC 信任度、心情的資料邊界
- 本系統的「歐姆城邦信任度」是群體／公共層次。
- 既有 NPC 系統中的「個別信任度」仍保留，代表某一位 NPC 是否相信玩家、認為玩家可靠；它與該 NPC 的好感度及當下心情仍是不同資料。
- NPC 個別好感、個別信任、心情及心理特質繼續依 V26.0 NPC 情感、心情與記憶系統運作。
- 不可把城邦信任度當成所有 NPC 個別信任度的平均值，也不可把科研聲望直接轉換成 NPC 好感。

#### 條件式連動原則
- 三項核心數值可以互相影響，但必須由具體事件、受益對象、實際成果及角色反應建立因果。
- 連動可以是小幅、延遲、局部或有條件的；不採固定比例、固定一對一轉換或單一行為全面刷高三項數值。
- 同一事件可能只影響其中一項，也可能在有充分理由時影響兩項或三項。
- 玩家公開分享研究成果、讓居民實際受益，才可能同時提高科研聲望與城邦信任；只完成私人研究、不公開或不影響居民的成果，不應自動提高城邦信任。
- 玩家與老馬克建立深厚關係，可能取得特殊館藏或研究線索；後續研究成果若達到學術標準，才可能增加科研聲望。個人友誼不直接等於學術評價。
- 玩家協助居民處理生態問題，可能增加城邦信任；實際受到幫助的 NPC 可能依個性與經歷增加好感或個別信任，但其他 NPC 不會集體同步增加。
- 參與益蟲交換日等社區活動可能提高城邦認同及參與者的個別關係，但若沒有研究成果，科研聲望通常不變。
- 公開違反城邦文化或制度可能影響城邦信任；只有與特定 NPC 的價值觀、利益或共同經歷相關時，才影響其個別好感／信任；科研聲望不應自動變動，除非事件同時涉及研究誠信或學術規範。

#### 禁止的簡化設計
不得採用「科研聲望 +10 → 城邦信任 +10 → 全部 NPC 好感 +10」等固定連鎖加分。系統應檢查事件實際影響的群體、個人與學術面向，避免玩家以單一行為刷滿所有關係。三項數值的顯示方式、數值範圍、權重、變化幅度與解鎖門檻仍待後續平衡。

- 博物館館長職責：管理館藏、展示、物種資料、歷史檔案及相關保育／研究活動。
- 知識導師職責：介紹物種、照護知識、生態箱維護、研究方法及生命福利。
- 舊版「老馬克同時是商店經營者」與 V25.0 已確認角色定位衝突，不納入目前正式規格。
- 老馬克祖父曾是地表旅人、曾來到歐姆，並留下生態箱工藝紀錄或未完成手稿，可保留為人物背景提案；其具體身分、年代、工藝貢獻及手稿內容待設計。
- 祖父故事不得直接推定為玩家的祖先，也不得因玩家姓氏為「歐姆」就自動觸發玩家血脈、特殊能力、獎勵或社會地位。
- 舊版「玩家姓氏為歐姆即觸發血脈的迴響」與 V25.1 已排除的姓名血脈獎勵方向衝突，暫不納入正式玩法。若未來保留相似彩蛋，必須重新設計為不違反既有稀有姓名規則的獨立劇情。

### 31.4 玩家姓名與雙階段揭露提案

**目前沿用的既有正式規則：**
- 玩家在歐姆戶政暨生物登記所建立地下姓名，姓氏與名字分開保存，並組成正式完整姓名。
- 玩家另有地表真實姓名，依雙重姓名與郵件規則保密及依來源情境使用。
- NPC 初期以正式稱呼為主；各 NPC 依個性、信任、關係階段、過往事件及情境，決定何時使用玩家名字或親近稱呼。
- NPC 稱呼不得使用全員共通的固定好感度 60 門檻。

**V16.0 雙階段命名提案：**
- 第一階段先讓玩家以地下姓氏／正式職稱被公開稱呼。
- 第二階段在玩家與特定 NPC 建立足夠信任後，才向該 NPC 揭露個人名字，並由該 NPC 在符合關係條件時使用。
- 此提案的核心價值是「個人名字的揭露具有私人信任意義」，而不是讓所有 NPC 在同一時間取得玩家名字。

**尚待確認的衝突：**
- 舊提案要求玩家在關係事件發生後才輸入個人名字；既有正式流程則是在初次戶政登記時選定姓氏與名字。兩者尚未決定採何種資料流程。
- 整合建議是保留玩家在開局登記時已建立完整地下姓名，但將個人名字的「對外揭露／個別 NPC 使用權」分階段開放。如此可保留私人信任感，也不破壞既有正式姓名、官方文件及存檔資料的一致性。
- 若使用者最後選擇延後輸入名字，必須同步重新設計登記所正式姓名、官方文件、地表包裹、存檔欄位及初期 NPC 對話，不能只改稱呼文字。

### 31.5 姓名文化與「歐姆・歐姆」例外

- 歐姆地下姓名的一般姓氏資料庫可以收錄「歐姆」。
- 一般名字資料庫不把「歐姆」列為普通名字。
- 「歐姆・歐姆」仍是獨立、罕見的完整姓名紀錄，不由一般姓氏與名字隨機組合。
- 此姓名不附特殊能力、地位、經濟優勢、血脈獎勵或文化懲罰。
- 舊提案「姓氏與名字完全相同一律不合法」不得套用到「歐姆・歐姆」這筆既有例外。
- 姓名驗證需區分一般自訂姓名、資料庫選項及獨立彩蛋紀錄；地表姓名不受歐姆地下姓名規則限制。

### 31.6 微觀生態與清潔生物教學

沿用 V25.2 第 30.1 節：研究站保留前任研究員留下、已有白跳蟲與球鼠婦穩定繁衍的舊生態觀察箱。V25.3 補充微觀觀察表現，不另建第二套生態箱規則。

- 白跳蟲及球鼠婦可作為微觀生態教學對象，觀察牠們在底材、落葉、腐木及適合微環境中的活動。
- 微觀觀察可呈現白跳蟲移動、球鼠婦取食、真菌與有機碎屑變化，以及底材局部環境。
- 分解者數量只是觀察線索之一，不得當作生態箱健康的唯一指標。
- 玩家可學習移動適量潮濕底材、落葉或躲藏物，將部分族群轉移到合適的新環境；舊箱須保留足夠族群，不搬空原有生態。
- 白跳蟲以含有族群的適量底材轉移為主；球鼠婦可在避免擠壓、乾燥及過度干擾的情況下輕柔轉移，或連同適當躲藏物及底材移動。
- 轉移成功與否須依物種適配、溫濕度、底材及新箱環境判斷。白跳蟲與球鼠婦不是所有寵物生態箱的通用配置；各初始寵物仍需依物種需求建立獨立飼養環境。
- 微觀觀察鏡的視覺形式、放大比例及互動成本待實作評估，優先採穩定、易操作的呈現方式。

### 31.7 系統責任與模組名稱

V16.0 提出的模組名稱只作功能責任參考，不構成必須新增同名檔案的要求。

- NPC 好感、個別信任、心情、記憶及稱呼應沿用既有 V26.0 NPC 系統，避免另建重複資料來源。
- 命名文化與玩家姓名顯示政策應與戶政暨生物登記所及雙重姓名資料整合。
- 植物、地質、底材及微觀生物資料可依現有百科／物種資料架構整合。
- 生物個體成長、健康、行為及生態箱環境需保持責任清楚，但不要求每個概念都獨立建立高負擔模擬系統。
- 博物館收藏、商店庫存及生態模擬均先檢查既有程式架構，避免過度拆檔與重複實作。
- 所有新增功能均遵守穩定遊玩優先；若第一人稱演出、微觀效果或模擬深度影響手機／桌面效能，應簡化或延後非核心效果。
